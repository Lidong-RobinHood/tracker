# App language (i18n)

English, German and Simplified Chinese, switchable in Settings › General › Language (Automatic,
English, Deutsch, 中文). The web app is the prototype of native apps, so the catalogue is plain data:
flat `key → text` with named `{placeholders}`, one file per namespace and language.

Namespace = folder: `src/food/**` → `food`, `src/ui/*` → `common` (info sheets → `info`), `src/app.js` → `app`,
workout analysis / progress / recovery screens → `analysis`, built-in names → `data`; texts that `src/core/*`
describes with keys go to the namespace of the feature showing them (table under "Text produced in src/core").

## Keys

- `namespace.area.name`, dot-separated camelCase: `settings.storage.notProtected`, `workout.session.finish`.
  The first segment is the file's namespace (the test checks it).
- Name by meaning and place, not by the English words: `settings.backup.title`, not `settings.timeForABackup`.
- One key per use when the context differs (a button and a title may need different words in German).
  Shared, identical-meaning words go to `common` (`common.today`, `common.exportBackup`).
- Never build sentences from fragments (`'Last ' + 'backup'`); one key per sentence with placeholders.
  Word order differs: German and Chinese move the number, the verb and "ago".
- Keep keys stable; changing the English text does not need a new key unless the meaning changes.

## Using t()

```js
import { t } from '../i18n/index.js';
t('settings.title')                                      // 'Settings'
t('settings.update.available', { version: '0.8.0' })     // 'Version 0.8.0 available'
t('settings.backup.days', { count: 3 })                  // plural: settings.backup.days_one / _other
t('settings.export.done', { count: n, n: fmtGrouped(n) }) // count selects the form, n is the displayed number
```

- **Plurals:** a numeric `count` param selects `key_<category>` with `Intl.PluralRules` of the active language,
  falling back to `key_other`. English and German need `_one` + `_other`, Chinese only `_other` (the test enforces
  exactly the language's categories). `{count}` inserts the raw number; pass a separately formatted value when
  grouping matters.
- **Fallback:** missing in de/zh → English; missing in English → the key itself, with one console warning.
- **Never call `t()` at module top level** (route tables, `const LABELS = {…}`): modules are evaluated before the
  catalogue loads, so the text would stay English. Store keys and translate when rendering
  (`TABS = [{ label: 'app.tab.diary' }]` → `t(tab.label)`); routes use `titleKey: 'settings.title'` instead of
  `title`. `t()` warns when called before `initI18n()`.
- Placeholders are `{name}` (letters, digits, `_`). An unknown/missing param stays visible as `{name}`.

## Dates

Use the helpers, never hand-made `['Mon', …]` / `['Jan', …]` arrays or string surgery on formatted dates:

| Helper | en | de | zh |
|---|---|---|---|
| `fmtDate(s)` (`src/ui/format.js`) | Wed 18 Nov | Mi. 18. Nov. | 11月18日周三 |
| `fmtDay(s)` | Today / Yesterday / Tomorrow | Heute / Gestern / Morgen | 今天 / 昨天 / 明天 |
| `dateLabel(d, { year })` | Wed 18 Nov 2025 | Mi. 18. Nov. 2025 | 2025年11月18日周三 |
| `dayMonth(d)` | 18 Nov | 18. Nov. | 11月18日 |
| `dayRange(a, b)` (no-break spaces inside a date) | 16–22 Nov · 30 Nov – 6 Dec | 16.–22. Nov. | 11月16日–22日 |
| `monthYear(d)` | November 2026 | November 2026 | 2026年11月 |
| `weekdayShort(i)` / `weekdayNarrow(i)` / `weekdayLong(i)` (0 = Mon) | Mon / M / Monday | Mo / M / Montag | 周一 / 一 / 星期一 |
| `monthShort(m)` / `monthLong(m)` (0 = Jan) | Nov / November | Nov / November | 11月 / 十一月 |

English keeps fixed abbreviations ('Sep', not ICU's 'Sept'); de/zh use `Intl.DateTimeFormat` with `getLocale()`.
`fmtTime` stays 24 h `07:03` in every language. `src/core/dates.js` has no names and stays as it is.

All hand-made date names were replaced by these helpers. `src/core/import-common.js` `WEEKDAYS` / months are for
*parsing* imported files (already multilingual) — leave them.

## Numbers (unchanged, decision pending)

All languages currently show `.` as the decimal mark and a narrow no-break space (U+202F) for thousands
(`fmtGrouped` → `1 310`, `fmtSigned` → `−0.5` with U+2212). `fmtNum` uses `String(round(n))`, so `12.5`;
`fmtTonnage` uses `.` too. Input: `numberInput` / `parseDecimal` accept `,` **or** `.` as the decimal mark
(only the first comma is converted; no grouping is accepted: `1.234,5` → invalid), `setNumber` writes `.`.
So German users can already type `0,5`, but see `0.5`. Switching display to `0,5` for de would touch `fmtNum`,
`fmtGrouped`, `fmtTonnage`, every `toFixed` in templates (25 places) and the values put into inputs.

## Do not translate

- Units and symbols: `kcal`, `kJ`, `kg`, `g`, `ml`, `min`, `h`, `t`, `%`, `×`, `–`, `·` (keep them in the text, not in keys).
- Brand and product names: Tracker, Open Food Facts, Anthropic, Claude, OpenAI, Google Gemini, YouTube, model names.
- User data: food names, exercise names the user typed, routine / meal / split names, notes, imported text.
- Prompts sent to photo-analysis models (`src/core/meal-photo.js`): the model answers in JSON; keep them English.
- Language names in the picker (`LANGUAGES`): always native (English, Deutsch, 中文).
- Data formats, file names (`tracker-export-<date>.json`), JSON keys, CSV header names the importers detect.
- Mark legit literals with `// i18n-ignore` (line), `// i18n-ignore-next-line`, `// i18n-ignore-start` … `-end`,
  or `// i18n-ignore-file`.

Seeded exercise names, split names and muscle names are translated at display time by id (namespace `data`,
see "Built-in names" below), never by rewriting stored records.

## Built-in names (data namespace)

Stored records are never rewritten. Seed exercises, library splits and their days, muscles and equipment are shown
by id in the app language while the stored name is still the English seed name (`isBuiltInName`); anything the user
created or renamed is shown as stored. Routines adopted or copied from a library split store the English day name
and show it translated (`routineName`); a workout stores its routine's stored name and `workoutTitle(w)` shows it
translated when it is an English day name of that routine's split (routine deleted: when the name belongs to
exactly one library day). Lists: `compareText(a, b)` (`src/i18n/index.js`, `Intl.Collator(getLocale())`) for
every alphabetical order; percentages: `withPercent()` (`src/core/numbers.js`, `62 %` with a no-break space).

## Generic foods

USDA foods keep their English name in the database and in backups (`source: 'usda'`, `sourceKey: 'usda:<fdcId>'`).
`src/data/generic-foods.de.json` / `.zh.json` hold the names in the order of `generic-foods.json`, composed from
translated name segments (`tools/build-food-names.mjs`, see `src/data/generic-foods.README.md`), with their own
fdcIds (`ids`) and English-name hashes (`en`, `nameHash`), so they are usable without the 0.8 MB base file. The
diary, the add screen and saved meals load only the app language's names file, and only when a generic food is
on screen (`ensureDisplayNames(foods)`); search loads the base file and both names files. Search matches English,
German and Chinese names (and the aliases of `generic-foods-common.json`, tagged by language) in every app
language; names are ranked by language (`nameRank`: app language 0, English 1, other 2) and a match only in another
language's name ranks below the app language's (`bucketOf`, `FOREIGN_PENALTY` in `src/core/food-search.js`). The
app language's name is shown (`foodName` / `itemName` in `src/food/names.js`) unless the user renamed the food
(its name no longer hashes to the English one). A broken names file is skipped, and those foods stay English.

A food found through another language's name keeps that language ("show the name as I typed it", SPEC §9):
`searchMatches()` (core) returns `{item, lang}` with the language each result matched in (names carry an
optional `lang` next to `rank`; `langNames` / `forLanguage` tag them; null = the app language), `asFound()`
(`src/food/generic.js`) turns that into a copy with `nameLang`, and `toFoodRecord` stores it on the food
(`nameLang` absent = app language; only the code is stored, the name stays English). Display goes through
`namesFor(food)` (`src/food/generic.js`; `shownNameLang` in `src/core/food-names.js`), and
`ensureDisplayNames(foods)` also loads the names files of the foods' `nameLang`.

## Dishes

The app's own dish estimates (`src/data/dishes.json`) carry their names and aliases in English, German and Chinese in
the file itself. A logged dish is stored like a generic food, language-neutral (`source: 'dish'`,
`sourceKey: 'dish:<id>'`, the English name) and shown by id in the app language (`dishName` / `itemName`,
`src/food/dishes.js`, `src/food/names.js`) unless renamed; the "name as typed" rule and `nameLang` apply exactly as for
generic foods (`NAME_LANG_SOURCES` in `src/core/food-names.js`). Search indexes names and aliases of all three languages
with the same ranks (`dishSearchNames`). New dish texts go into `tools/dishes/recipes.*.json` (all three languages
required by the build). UI words: Dishes, ≈ Estimate, Small / Normal / Large (glossary).

## How to add a language

1. Add `{ code, name }` (native name) to `LANGUAGES` and a tag to `LOCALE_TAGS` in `src/i18n/index.js`; extend
   `detectLanguage()` for its codes.
2. Copy `src/i18n/en/*.js` to `src/i18n/<code>/` and translate every value (keep keys and `{placeholders}`).
3. Plurals: add exactly the categories of `Intl.PluralRules(<tag>)` (the test lists missing / extra forms).
4. Dates: add its names / patterns to `src/i18n/dates.js` if `Intl` output needs adjusting (see the en/de/zh cases).
5. Boot-failure text in `index.html` (inline table) and the language picker in Settings › General.
6. Generic food names: translate `tools/food-names/<code>.json`, run `compose <code>`, add it to `NAME_LANGS`
   (`src/food/generic.js`) and `COMPLETE_LANGS` (`tools/build-food-names.mjs`). Dishes: add the language's names and
   aliases to `tools/dishes/recipes.*.json` and `tools/build-dishes.mjs`, then rebuild `dishes.json`.
7. Extend the glossary (`docs/I18N-GLOSSARY.md`) before translating.
8. `npm test` (catalogue consistency), check every screen at 375 and 320 px, `node tools/build-precache.mjs`.

## Language choice, storage, switching

- Choice: `'auto'` (default; `navigator.languages`: first `de*` → de, first `zh*` → zh, first `en*` or none → en),
  `'en'`, `'de'`, `'zh'`.
- Stored twice: localStorage `tracker.language` (read synchronously at boot so the catalogue loads in parallel with
  IndexedDB; `auto` = key absent) and settings key `language` (so export / import carry it; no schema change).
  At boot (`src/app.js` › `syncLanguageSetting`) the settings value wins when it differs (a backup was imported) and
  is copied to localStorage; a device choice missing from the settings (old backup) is written there.
- Switching: Settings writes both and reloads the page; every screen renders again with the new catalogue.
- `<html lang>` follows the language (`en`, `de`, `zh-Hans`).

## Rules for translators

- German: informal **du**, sentence case like the English, short UI words (mainstream fitness apps: Training,
  Satz/Sätze, Wiederholungen, Übung, Trainingsplan, Tagebuch, Ziel). German quotes „…“; `…` as in English.
- Chinese: Simplified, concise, full-width punctuation (，。：；？（）“”、), a space between Chinese and Latin letters
  or numbers (`已用 4 MB`, `你的 API 密钥`), no space around full-width punctuation.
- Keep `{placeholders}` exactly (names are checked by the test); you may move them. Keep units, brand names and `×`.
- Plurals: German `_one` + `_other`; Chinese `_other` only.
- No exclamation marks, no emojis, sentence case (copy-audit glossary in `docs/CONTRACT.md` › How to restyle, 6).
- Check length: tab labels and row titles must fit at 320 px (titles in Settings wrap; buttons do not).
- Use the binding glossary `docs/I18N-GLOSSARY.md` for every namespace; the same English in the same sense gets the
  same translation everywhere (several namespaces have their own Save / Cancel / Done keys: keep them identical).

## Checklist for a converting worker

1. Run `node tools/i18n-scan.mjs src/<folder>` for your to-do list.
2. Add English keys to `src/i18n/en/<ns>.js` (move texts unchanged; fix only obvious plural bugs), call `t()` in
   the code. No `t()` at module top level; route `title` → `titleKey`.
3. Replace hand-made date names with `src/i18n/dates.js` / `fmtDate`; do not parse formatted dates.
4. Texts from `src/core` you call: change core to return keys / data (see above); never translate inside core.
5. Keep `src/i18n/de|zh/<ns>.js` complete and free of stale keys (`PENDING` in tests/i18n.test.js is empty:
   every key must exist in de and zh).
6. The scan must stay at zero for all of `src/` (`CONVERTED = ['src']`); use `// i18n-ignore` only for units,
   brands, formats.
7. Check your screens in en / de / zh at 375 and 320 px (light and dark): no clipping, no horizontal scroll.
8. `node tools/build-precache.mjs`, `npm test`.

Release: `PENDING` empty (it is), `node tools/i18n-scan.mjs --check` exits 0.

## Native apps later

Each `src/i18n/<lang>/<ns>.js` maps 1:1 to a `Localizable.strings` / `strings.xml` per language: key unchanged
(Android: dots → underscores), `{name}` → `%@` / `%1$s` (positional order taken from the English text),
`_one` / `_other` groups → `.stringsdict` / `<plurals>`.
